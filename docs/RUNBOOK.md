# Аварийный порядок: что делать руками

Порядок для ночи, для «панель не отвечает», для «подписчики не доходят». Каждый
шаг называет, что он меняет и чем откатывается. Адреса коробок здесь не
пишутся — по открытому литералу чужой сканер опознаёт узел, не глядя на адрес;
вместо них `<БЭК>` и `<ФРОНТ>`. Кому принадлежит какой адрес — живой список
лежит вне репозитория в `<ПАНЕЛЬ>/.scratch/ТОПОЛОГИЯ.md` (не индексируется):
прежде чем судить про «фронт» или «бэк», читать его, а не выводиться заново.

Проверить, что панель жива, всегда дешевле, чем чинить вслепую:

```bash
systemctl status vpnpanel --no-pager | head -20
journalctl -u vpnpanel --since -30min -o cat | grep -iE "traceback|error" | tail
tail -40 <ПАНЕЛЬ>/logs/panel.err
curl -sk -o /dev/null -w "код=%{http_code}\n" https://127.0.0.1:8443/
```

## 1. Подписчик не доходит: три слоя, по порядку

1. **Имя.** Чем оно сейчас разрешается: `hop_public_host` в
   `<ПАНЕЛЬ>/config.json`. Если там адрес фронта — смотреть слои 2 и 3; если
   адрес бэка — фронт ни при чём, идти к слою 3.
2. **Фронт.** На нём живут два механизма: релей `veil_relay` (DNAT входов на
   туннель) и щит `veil_fsh` (SYN-ограничение и серый набор).

   ```bash
   ssh root@<ФРОНТ> 'cat /etc/veil-relay/relay.env; \
     systemctl is-active veil-relay veil-relay-keeper; \
     systemctl is-active "awg-quick@veilhop0"'
   ssh root@<ФРОНТ> 'nft -a list chain ip veil_fsh pr'
   ```

   Имя туннеля — `TUN_IF` из `/etc/veil-relay/relay.env` (без слова —
   `veilhop0`), его и подставляют службы `awg-quick@<туннель>`. Шесть правил с
   комментариями `fsh_*` — щит на месте. Седьмое с комментарием `fsh_maint` —
   это замок паузы (§7): новые соединения на входы фронта отбрасываются нарочно.
   Если паузу никто не включал, а правило лежит — снять
   руками: `nft delete rule ip veil_fsh pr handle <handle>`.
3. **Бэк.** Таблицы две: `inet veil_synfix` (SYN-защита входов) и
   `inet veil_bans` (банеры входа в панель).

   ```bash
   nft list table inet veil_synfix | head -40
   nft list set inet veil_bans b4 | head
   ```

   Живой клиент, угодивший в бан, снимается словом из UI («Разбанить»), а если
   UI недоступен — прямо с машины:
   `nft delete element inet veil_bans b4 { <адрес> }`. Множества с `timeout`,
   поэтому бан отваливается и сам.

## 2. Пауза фронта: включить, снять, снять, когда панель не может

Штатная дорога — карточка «Двойной прыжок»: «Пауза фронта» и «Возобновить
фронт», морда спрашивает имя оператора, оно попадает в журнал.

Возобновление честное: фронт сначала поднимает свои сервисы, с него снимается
замок, и только потом меряются три свидетеля (стук смотрителя, TCP-пробы
входов, зонды из РФ). Непроверенный фронт получает отказ словами, а не
обещание. Если до фронта нет SSH, а имена срочно нужны на нём:

1. кнопка с обходом проверки (`force`) — отказ записывается в журнал как
   обход рукой, а не как «проверено»;
2. или сказать слово прыжку вручную (карточка / `/api/hop/public`), после чего
   снять замок на фронте командой из п. 1 — иначе имена ведут на фронт, а его
   порог держит новых клиентов.

Забытый замок опаснее самой паузы: панель заметит это на следующем тике
(перекладывает раз в минуту) и запишет `hop_maint_lock_lost` /
`hop_maint_lock_repaired`, но ей нужен ход наружу до фронта.

## 3. Панель не поднимается после правки

Выпуск всегда откатываем. На боевой машине перед установкой лежит снимок
предыдущих байтов:

```bash
ls -la /root/rel-*/            # panel-before.py, index-before.html
python3 -m py_compile <ПАНЕЛЬ>/panel.py || echo "байты битые"
```

Откат — это возврат тех байтов и перезапуск, ничего умнее:

```bash
cp -a /root/rel-<ВЕРСИЯ>/panel-before.py <ПАНЕЛЬ>/panel.py
cp -a /root/rel-<ВЕРСИЯ>/index-before.html <ПАНЕЛЬ>/index.html
systemctl restart vpnpanel && systemctl is-active vpnpanel
```

`config.json`, `state.json`, ключи и подписки при этом не трогаются: выпуск
меняет код, а не состояние. Состояние переживает и рестарт, и откат — пауза,
запрет автовозврата и выбранный адрес бэка живут в `config.json` именно для
этого.

## 4. Автоматика дёргает имена: что нажать, чтобы она встала

Каждое движение имеет своё слово-выключатель — все они в
[SETTINGS.md](SETTINGS.md):

| Что происходит | Что выключает |
|---|---|
| Возврат имён на фронт по пробам | `hop_recover.off = 1` (мерить не перестаёт, слово не двигает) |
| Возврат на прежний адрес бэка | `back_addr_return = 0` |
| Перенос серых адресов бэка на фронт | `fsh_grey_share = 0` |
| SYN-защита бэка вообще | `synfix_enabled = 0` — последний вариант: коробка остаётся без защиты, и включать обратно надо осознанно |
| Любое переключение сразу | руки нет: ворота решения (`_failover_gate`) сами закрываются, когда качели посчитаны, — карточка показывает `auto_closed` |

Отдельный случай: автоматика молчит, хотя фронт жив. Так и должно быть, если
главный адрес бэка поставлен рукой (`back_addr_pref_by = "рука"`) или если
панель не помнит, кем он поставлен, — она не перешагивает оператора. Это не
поломка, это §4; возврат — отдельной кнопкой.

## 5. Фронт перезагрузился и щит пересобрался

Установщик щита перекладывает таблицу целиком (`nft delete table ip veil_fsh`),
и всё, что в неё вставило другое правило, стирает. Это известно и учтено:
замок паузы возвращается панелью за минуту, туннель и смотритель поднимаются
шагом PLAY, а релей и щит — их же установщиками, которые панель вызывает, если
таблицы нет:

```bash
ssh root@<ФРОНТ> '/usr/local/bin/veil-relay-apply.sh; /usr/local/bin/veil-fsh-apply.sh'
```

Оба идемпотентны по тегу в `/run/veil-relay/`; тег в `/run` живёт до
перезагрузки — после неё установщик отрабатывает заново.

## 6. Нет доступа в панель

- **Троттлинг и баны входа** (`veil_bans`) не банят приватные адреса и свой
  сеанс; если всё-таки банит — снять элемент с `<БЭК>` (п. 1, слой 3).
- **Пароль потерян, passkey не принимается**: вход по паролю остаётся запасным;
  восстановление владения — прямой разговор с хозяином коробки, в `config.json`
  лежат его порог прав и токены.
- **Сертификат протух**: выпуск делает панель (`certbot certonly`, DNS-01 или
  standalone), продление — штатный цикл `certbot renew` на машине по файлу
  `certs/renewal/veil-<домен>.conf`; пакет ставит `install.sh`. Если ручка
  отказала, временный вход — `https://<адрес>:8443` с панельной заглушкой,
  а не обход проверки имени.

## 7. Потеряна машина

Состояние подписчиков — `state.json` (входы и клиенты), ключи протоколов,
сертификаты и `config.json`. Панель умеет выносить и вносить своё состояние
(экспорт/импорт в UI, центр обновлений), а переезд на новый VPS делается штатной
дорогой «Переезд» с переносом порт-в-порт — ссылки подписчиков при этом не
меняются. Ручная дорога: снять `config.json`, `state.json`, `certs/`,
`node_keys/`, `sessions*.json`, `passkeys.json` и поднять панель установщиком
выпуска на чистой Ubuntu, вернув файлы на то же место. Приватные файлы нигде не
публичны: они накрыты `.gitignore` и не уезжают в переносе состояния наружу.

## 8. В дерево залезло два захода

Правки `panel.py` и `index.html` терялись молча: второй заход (другая сессия,
рука хозяина, ночной цикл) клал свои байты поверх моих, и выпуск уезжал без
того, что уже было написано. В истории такого коммита нет — потеря ничем не
отмечена, её можно только заметить якорем байтов.

- Перед правкой — якорь: `sha256sum panel.py index.html` (первые двенадцать
  байтов) ложится в строку `.relwork/STATE.md` вместе с замером. Перед коммитом
  — тот же вызов: число не совпало с ожиданием ЗНАЧИТ, в дерево кто-то вошёл, и
  сначала надо прочитать чужие байты (`git diff`), а не перекладывать свои.
- Один писатель на файл. Если заход не мой — правка становится латкой поверх
  живого текста (`Read` + `Edit` по месту), а не откатом чужого; `git checkout
  -- panel.py`, `git restore` и `git stash` без предварительного `git status`
  в этом дереве запрещены: они выбрасывают чужую работу так же молча.
- Приборы (отдельные прогоны `python3 .relwork/cc<№>_..._test.py`, подборки
  выпуска `.relwork/gates<цикл>.sh`) работают копиями и песочницами и дерева не
  трогают (#55); если прибор написал в рабочее дерево — это дыра прибора, а не
  рабочая байта.

## 9. Конфиг службы переложен, а служба стоит по-прежнему

Панель перекладывает конфиги служб (telemt, nginx, вставки systemd, sysctl,
logrotate, sshd, netplan, ключи из копии) ЦЕЛЫМ файлом: пишет временное имя
рядом, потом одна замена (`_conf_write`, выпуски 2.17.128–2.17.129). Смысл
для аварийного шага такой: если служба не перечиталась, виноват НЕ
оборванный файл — прежний конфиг ни при каком исходе не может остаться пустым
или надкушенным. Смотреть надо на другое, по порядку:

1. перечиталась ли служба вообще: `systemctl status nginx telemt ssh` и
   `nginx -t`. Панель делает `reload` только после успешной проверки;
2. дошёл ли ход до конца: `journalctl -u vpnpanel --since -15min` — у
   перекладки есть слово отказа, молчания она не оставляет;
3. не осталось ли временных имён: `ls -a /etc/nginx/conf.d /etc/telemt
   /etc/systemd/system/*.d | grep '\.tmp'` — после отказа мусор подчищается,
   найденный файл значит, что писатель умер снаружи (OOM, перезагрузка);
4. не уплыл ли mode: `stat -c '%a %n' /etc/telemt/telemt.toml` обязан быть
   0600 — mode берётся с прежнего файла, так что 0644 здесь означает чужую
   руку, а не панель;
5. если конфиг нужен абоненту, а не службе: раздаваемые базы, обои и значок
   идут тем же способом (`_ruleset_publish`), и пустой файл на раздаче теперь
   возможен только как целая прежняя картинка — проверяй, что именно лежит в
   копии состояния, а не «дописалось ли».

Откат после красного `nginx -t` возвращает файлам РОВНО прежние байта (замер
прибором cc129, ноги T4 и T7): половины в новом виде после такого отказа не
бывает. Если половина всё-таки есть — отказ пришёл не от проверки конфига, и
искать надо в канале до фронта (SSH-рука, права, чужой файл на пути).

## Что проверяется после любого аварийного шага

1. `hop_public_host` и слово паузы совпадают с тем, что ты хотел;
2. на фронте ровно та набор правил, что должен держать (с замком или без);
3. подписчик получает рабочий конфиг: `curl -sk https://127.0.0.1:8443/sub/<токен>`
   отвечает непустым телом;
4. `journalctl -u vpnpanel --since -10min` не печатает traceback;
5. вестка хозяину ушла, а журнал (`audit.json`) содержит сделанное действие с
   именем руки.
